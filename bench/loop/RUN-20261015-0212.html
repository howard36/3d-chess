Flag: a review now holds more memory than the bench measures

The run’s memory rule flags any peak increase over 5%. The page’s own heap did not grow (a reopened long game: −0.1%). But a review now runs up to three workers instead of one, and the bench does not measure workers. By estimate, each extra worker holds its own JavaScript heap and 3.25 MiB of search tables (ledger M9′), so a review on a 4-core machine may hold about 10 MB more while it runs, and frees it when it ends. Against a page heap of about 14 MB that is well over 5%. It is not measured.

Recommendation Keep the parallel review, and let the next run measure the workers’ memory (Chrome’s memory tools can) and make the search tables once per worker (M9′), which removes most of the per-position allocation.

Changed

A phone downloads the start page’s own picture, and shows it in half the time

The start page shows a picture of its 3D preview until the preview has loaded. A small script in the page’s head starts that picture downloading early, choosing the phone, tablet or wide picture from the window’s size. The build placed the script before the tag that tells a phone to use its own width, and until that tag is read a phone reports a 980-pixel-wide window. So every phone chose the tablet’s picture (73 KB), and the phone’s own picture started downloading only when the page drew it.

The script now follows that tag (commit 0c7aea0). A unit test fails if it moves back, and the bench now counts the pictures each cold load downloads. On the slowed phone, the board appears at 870 ms instead of 1.70 s, the page downloads 12% less, and “Play a friend” is ready 3.5% sooner (not called). One diagnostic got worse. On the phone without slowing, the first paint comes 76 ms later (146 → 222 ms), because the picture has already arrived and the first frame now includes it. The board on that phone appears 8.5% sooner.

A finished game’s review searches in several workers at once

A review searches each position of the game for a fixed number of positions (120,000), so its marks are the same on any machine. It used to search one position at a time in one worker. Each position is a separate search, so they can run side by side with the same results. The review now uses one worker per spare core, at most three, and hands the positions out from the start of the game (commit b305f6d). The marks were identical in all 16 runs of the A/B, and the page showed no freezes.

A review whose search failed used to show “done” with its counts as if final, so a review that failed at the first move read as a perfect game. Now it says “Analysis stopped” with a Retry button, which continues from the positions already found. The diff review found that a search finishing after the stop could restart the progress bar for good; that is fixed with a test (4b7fb96). The grading found that when the review cannot use workers it runs its searches on the page’s own thread, three at a time instead of one. 9afbf60 fixes this only for a browser with no workers at all (with a test). When a worker’s script fails to load (a stale file after a deploy, say), each of the three still falls back to the page on its own, so the page can be busy three times as long. That case is not fixed; it is first in Next.

The server’s tests now catch a lost write-back, and one large message can no longer stall every game

Each change to a game record is read, changed and written back. In production the store hands out copies, so the write-back is the whole change. The tests used a plain dictionary, which hands out the record itself, so a missing write-back passed every test. The tests and the local server now use a store that copies the way production does (commits fea5a5a and 2e17292). Removing a write-back now fails two tests; on main all 77 pass.

Every message is checked against all 31 message types. A 1 MB message made of 100,000 short keys took 7.4 s to check on this machine, and the server handles all games on one thread. Messages longer than 4,096 characters are now refused before they are read (cfbace2); the longest real message is about 150. A rejoin now sends every field the stored record shares with the protocol, instead of a hand-kept list, and its test reads the field from the rejoin (10ce347).

A focus bug my own cleanup caused, fixed

Merging the six offer lines into one table (1d1ca66) made React reuse one element for whichever line shows. With a take-back and a draw offer both standing, a keyboard player who declined the take-back kept focus on the same button, which then declined the draw. The diff review caught it, and keying each line by what it says fixes it (4b7fb96). This fix has no test.

A rematch keeps its seat when the browser refuses to save it

When local storage was full or turned off, accepting a rematch opened the new game with no saved seat, and the page showed “Game full” for the game the player had just been placed in. The page now also carries the seat in its navigation (9ba343a).

A reviewer suggested that the preview’s code, loading at the same time, held the picture back. Catching JSON nested too deeply

I added a catch for this with the size cap. The diff review pointed out that a message under 4,096 characters can nest at most 2,047 levels, which Python parses without trouble, so the catch could never run. I removed it.

Choices made alone

  • The review uses one worker per spare core, at most three. On a 4-core phone that is three workers during a review, using up to about 10 MB more memory while it runs (not measured).
  • The words “Analysis stopped” and “Retry” for a failed review.
  • Messages over 4,096 characters are refused with “Message is too large”.
  • The local server, e2e and the bench now copy records the way production does. Seeding a 2,000-move game in the bench takes longer (bench setup only, not a measured moment).
  • I accepted the later first paint on the unthrottled phone, since the board itself appears sooner.
  • The branch is pushed as claude/serene-galileo-jajbb3, the session’s branch, not improve/20261015-0212.
  • I folded the dependencies reviewer into the “what’s new” reviewer: every dependency is current (three r186, react-three-fiber 9.8.1, Vite 8.3.4).

  • The workers’ memory during a review. The bench measures the page’s memory, not the workers’.
  • Whether Modal’s own front end accepts frames larger than 4,096 characters at all; the cap holds either way.
  • The full e2e suite on this machine. It ran in CI on the merge commit and passed; here I ran the six specs the changes touch (14 tests, all passing).
